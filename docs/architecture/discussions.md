## 可复制的新会话开场

```text
我们正在设计 LifeCore（生命核心），仓库为 sealbell/LifeCore。
请先阅读 README.md、docs/architecture/v1.md、docs/architecture/discussions.md，
再按需要阅读 docs/project-design.md 中的背景和参考源码。

本次详细讨论模块：【填写模块编号和名称】。
目标是明确它要做什么、怎样工作、输入输出、数据归属、失败处理、
隐私边界、依赖模块与验收场景。先讨论，不写产品代码或安装依赖。
需要保存文档时，写入 docs/architecture/modules/ 下对应模块设计，
并在 discussions.md 登记链接和状态；不要把待定选择写成已获确认。

共同约束：DSH 插件，外部软件不打包；一个正式生命；
多场景独立上下文；人格有历史惯性；事实、解释、意图和结果分开；
统一状态提交；权限先于检索；恢复不能重新发送历史动作。

请先说明你从现有设计中确认的内容，以及这次最需要解决的设计问题。
```

此模板供维护者主动开启会话时使用，不自动创建或发送到新会话。

## 单个模块设计应交付什么

1. 目标、非目标、具体使用情景和反例。
2. 从 V1 继承的约束，以及本次新做出的决策及理由。
3. 输入、输出、调用方、可信边界、状态/数据归属。
4. 正常流程、状态转换与关键算法；参数区分实验提案和已确认值。
5. 失败、重复、并发、取消、离线、重启与恢复行为。
6. 隐私、删除、诊断、预算及可解释性要求。
7. 与其他模块的接口契约及需要同步修改的文档。
8. 可观察的验收场景、待决问题、引用的源码提交与兼容性证据。

文件命名建议 `modules/Mxx-english-name.md`。首次讨论完成再创建实际文件。
状态采用“待详细设计 → 讨论中 → 待确认 → 已确认”；实施进度另行记录，设计确认不等于功能完成。

## 避免不同会话互相冲突

- 每次开始读取当前文件与 Git 状态，不只依赖旧聊天记忆。
- 跨模块字段、权限和提交协议的改动必须写回 V1，并列出受影响模块。
- 已存在的详细设计优先复用；与 V1 冲突时明确提出修订，不能静默覆盖。
- 参考项目的分支代码可能变化，代码复用前固定提交并保留来源与许可声明。
- 在维护者明确要求实现前，不从模块讨论直接跳到脚手架或产品代码。
