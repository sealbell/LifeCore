## 1 要解决的事情

目标不是让一个模型把一生始终装在单次上下文里，而是让“大肥鱼”的身份、经历、关系依据和未完事项独立于某一次模型请求存在。新会话重新获得这些状态，需要某件往事时能找回它的原始依据，然后自然地接着交流。

用户已经明确的目标：初始人格来自人格设定卡；后续共同经历能够累积；重要事情自动保留；新会话不需要重新认识；能查看、纠正、删除记忆；主动联想是独立可选开关。本文沿用单 DSH 插件、单正式生命、无独立 LifeCore 服务器、数据独立于插件安装目录的已确认边界。

本次新增的工程选择由设计者提出：SQLite 事务日志、原文与派生表示分离、双时间事实、混合召回、相关性门槛、按预算展开证据、每轮独立生成上下文、持久化整理队列。它们尚未被标记为用户逐项确认。原 M04/M09 的“向量后置”调整为“基础闭环先落地，完整目标架构包含经过验证的中文语义检索”，不是静默修改既有结论。

非目标：证明意识、把模型权重训练成个人档案、无限上下文、离线虚构生活、用本次设计实现全部十五模块。记忆模块不替代人格/关系/承诺的权威状态机，也不直接操作外部平台。

失败判据：原始聊天只留下摘要；重开会话丢身份；相似但无关的回忆挤入回答；新偏好被旧偏好覆盖；把计划当已经发生；“已记住”却未持久化；删除后又从备份复活。

## 2 为什么选这个组合

| 路线 | 优点 | 对本项目的不足 | 决策 |
| --- | --- | --- | --- |
| 固定记忆卡 + 滚动摘要 | 简单、省成本，启动连续感容易做 | 细节不断压缩；固定栏目不知道当前问题；记忆长大后互相挤占 | 仅用于小型启动视图和工作摘要 |
| 原文/事实向量 RAG | 能按语义找资料，易扩展 | 不能独自处理身份、时间变化、完整经历、中文精确词和无关相似项 | 作为召回的一路 |
| 原文账本 + 多种派生表示 + 混合召回 + 证据组装 | 能恢复、纠错、追踪来源；分开保障保存与使用；符合插件形态 | 写入、索引、失效和评价更复杂 | 推荐完整路线 |

不强制部署全图数据库。先以 SQLite 关系表存有类型的事件关联；只有多跳问题的实测增益足以抵消复杂度时再升级。参考依据见 R01/R03/R04/R11/R14；这些项目支持这个组合的若干机制，并未共同证明该组合已达到某个准确率。

## 4 保存什么：六种互相连接的材料

### 4.1 原始事件账本：保存发生过的记录

保存允许留存的入站文本、发送成功的出站文本、平台编辑/撤回、工具执行与回执、管理纠正等。默认不按重要度丢弃允许留存的文字；“普通闲聊”也可能将来变得重要。

保存源数据与规范化表示。规范化不得覆盖原文本；时间转换、分词、实体标记均为附加字段。图片/音频如获准保存则保存附件与校验值；无法下载、平台未提供或策略禁止保存时明确标为缺失，不能宣称已保留其完整内容。转写/图像描述是派生解释，不是原媒体。

入库前必须执行既有 M12 保留规则；明确禁止留存的秘密不会为了“全量”进入普通账本。记录不可逆脱敏/丢弃发生的范围及原因，不记录被禁止内容。本文所有“原文完整”均指系统实际收到且获准保留的内容。

### 4.2 事实记忆：回答具体问题

例如：称呼、生日、偏好、目前居住地、明确边界。事实包含主体、属性、值、适用场景、来源陈述者、有效时间、系统记录时间、版本与争议状态。

“用户说喜欢咖啡”保存的是有来源的自述；不是外部验证的客观事实。玩笑、假设、转述和否定需要显式模式，不能都转成用户属性。姓名相同不允许自动合并人。

### 4.3 经历记忆：保存共同故事

一个情节可以跨多轮/多天，例如一起修改项目、一次误解及和解、一个约定的形成。包括参与者、时间范围、起因、关键事件、实际结果、仍未解决之处、证据事件序列。

M03 负责情节身份和成员关系；M04 生成长短不同的可检索表达。默认根据明确回复关系、同一任务标识、参与者/主题/时间综合提出关联；单纯“主题相似”不足以合并。可先保持独立，再建立“同系列”关系。重要时刻是情节标记，不再复制一份独立事实。

“你告诉我去海边旅行”≠“我们一起去了海边”。她参与的是这次讲述或讨论；共同经历的动词必须与事件一致。

### 4.4 连续性视图：新会话恢复认识

小型物化视图，不是第二个真相库：

- life_id、人格卡版本、正式出生状态。
- 本场景合法可知的对方身份、称呼与关系依据。
- 少量持续有效的沟通边界。
- 与当前场景有关的开放情节、未完问题和承诺状态引用。
- 已知最早相识事件入口、近期连续性入口；通常保留短描述和 ID，不塞全部详情。

身份绑定来自 M06 的可信账号映射。新会话 ID 不改变 life_id/person_id；平台昵称变了也不自动变成陌生人。另一账号是否同人须按 M06 核实；绑定同人不自动开放跨场景隐私。

视图必须带源版本与策略版本。查不到或校验失败时标为 unavailable，禁止创建新生命来“修复”。对于未知访客按未知主体正常交流，不套用主人的档案。

### 4.5 工作记忆：接得上正在谈的事

每个 conversation_id 独立存：近期原文窗口、已覆盖区间的工作摘要、当前话题、未答问题、待确认项。摘要不是递归压缩后的唯一材料；定期从原文范围重建并保留版本。

新开宿主会话可在权限允许时选中同一对话分支的工作头；同时有多个话题分支时仅载入相关头和简短导航，不能拼出一个混杂的“最近聊天”。切换平台不意味着复制上个平台私聊的工作摘要。

### 4.6 理解、重要性和索引

反思是“她如何理解这段经历”，保存 interpretation 类别、来源与不确定性；不能升级为新的客观证据。重要性用理由（明确要求记住、首次、共同投入、转折、持续影响）表示。

关键词、embedding、实体别名、时间索引、关联边都是可重建的查找入口。重要性影响维护优先级、展开深度和相关候选的排序，不决定原文是否保存，也不豁免权限或相关性。

## 5 可实施的数据模型

以下是逻辑存储契约；SQLite 列类型、迁移 SQL、索引实现由实施者据此细化，不能更改其语义。

| 表/集合 | 关键字段 | 约束与用途 |
| --- | --- | --- |
| lives / persona_versions | life_id, birth_event_id, persona_version, status | 一个正式生命；出生与恢复分开 |
| identities / identity_bindings | person_id, platform, account_id, binding_version | 昵称不作主键；M06 管理绑定 |
| scopes / policies | scope_id, policy_version, disclosure_rules | 场景与主体不同；M12 管理 |
| source_events | event_id, life_id, source_key, source_revision, conversation_id, actor_id, kind, received_at, occurred_at, raw_payload_ref, content_hash, scope_id, status | unique(life_id, source_key, source_revision)；事实权威输入 |
| event_chunks / attachments | event_id, version, offset_start/end, payload_ref, hash, availability | 块偏移指向具体原文版本；附件有缺失状态 |
| source_cursors | adapter_id, stream_id, last_contiguous_offset | 与入库事务同步更新；有序流缺口不能越过 |
| episodes / episode_members | episode_id, version, participants, time_range, event_id, relation | M03 权威；成员关系可更正留版本 |
| memory_versions | memory_id, version, kind, subject_id, predicate, value_json, text, valid_from/to, time_precision, recorded_at, supersedes, status, evidence_class, importance_reasons | 历史版本保留；只允许规则认可的当前头 |
| memory_sources | memory_id, version, event_id, source_revision, span, claim_id | 每个重要断言对应具体来源；多来源不能丢溯源 |
| memory_links | from_id/version, to_id/version, type, evidence_refs, status | elaborates/same_series/contrasts/causes 等；推断因果标为解释 |
| working_heads / continuity_views | conversation_id或person_scope_key, version, covered_ranges, source_deps, content | 可重建，不能覆盖底层历史 |
| jobs / index_outbox | job_id, type, input_ids_versions, extractor_version, idempotency_key, lease_until, attempts, state, error | 原文与待办原子提交；队列有持久状态 |
| coverage | source_id/version, stage, state, output_refs, processor_version, reason | 区分未处理、成功、无事实、失败、策略排除；不能把漏处理当无信息 |
| index_manifests | generation, namespace, model_revision, dimension, tokenizer_revision, covered_ranges, status | 索引版本与来源范围可核对 |
| turns / context_packets | turn_id, scope, input_event_id, source_snapshot, dependency_versions, policy_version, manifest, token_usage, status | 记录选了什么、为什么选、模型读到什么 |
| outbound_actions / receipts | action_id, turn_id, destination, content_ref, state, idempotency_key, receipt | 生成、发送、确认、未知分开；M11 权威 |
| tombstones / restore_fences | deletion_id, target_refs, policy_version, deletion_epoch, restore_generation | 防止已删除材料从旧索引/备份再次可用 |

所有业务表属于 life_id 或隔离 trial_workspace_id，不能空值回落全局生命。person_id 是谈论对象，actor_id 是谁说的，conversation_id 是话题/对话分支，scope_id 是可见范围，DSH session_id 是一次宿主运行身份；五者不可混用。

事件行可记录后续可用性变化，但正文修订用新 source_revision；派生内容更新用新 version。正常保留阶段 append-only，用户删除/保留到期是明确例外，不以“不可变日志”为理由拒绝删除。

## 6 写入：先留下记录，再理解它

### 6.1 同步接收事务

1. M10/M14 校验消息来源及格式，分配稳定 source_key。优先使用平台消息 ID + 平台账号/会话范围；相同文字的两条消息不能按 hash 合并。
2. M12 判定保留规则，M06 解析主体，M02 开启短事务。
3. 写 source_event、完整文本、分块引用、基础检索词、整理任务与一致性脏水位；对需要回复的入站消息，同时创建唯一 turn 占位和 reply job；更新连续来源游标；提交。
4. 只有提交成功才在内部返回 accepted=true。支持接收确认的平台在这之后确认；不支持的平台保留来源重放能力，不能假装有端到端确认协议。
5. 当前消息进入回复管线。LLM 抽取和 embedding 均不在写事务里等待，不阻塞数据库。

同一源事件重送返回既有 event_id；不会重复成长或重复回复。平台消息编辑生成新修订并使旧派生表示进入待更新；撤回/删除按 M12 区分“平台状态变更”与“本地清除要求”，不擅自把两者视为同一种操作。

reply job 的幂等键为 life_id + input_event_id + reply_kind；turn 从 accepted 状态开始。是否需要回复由可信接入路由决定并记录 trigger/skip_reason，发送回执与后台维护事件不会再次触发对话回复。进程内唤醒只是加速，启动及周期扫描必须领取持久 pending job。不存在“先确认事件，之后才首次创建回复任务”的窗口。重复输入即使不直接驱动回复，原有 job 仍会恢复；startTurn 只以租约/CAS 领取已存在的占位，只有一个执行者可推进该轮。

附件先写临时文件并同步，原子改名到内容地址路径，再提交数据库引用；崩溃后的孤儿文件可清理，已提交记录不得引用未完成文件。无法可靠执行时先提交“附件待取回”状态，完成后新事件补齐，不宣称媒体已保存。

### 6.2 异步整理

持久任务状态：pending → leased → running → succeeded；失败进入 retry_wait，达到重试上限进入 failed_visible。租约超时可被重新领取；输出以幂等键和输入版本提交。

默认提案：每个获准事件都进入覆盖账；每次闭合交流单元后或 30 秒空闲时提交小批整理，批次上限约 2,000 输入 tokens；明确“记住”、纠正、约定优先。会话边界与引用链优先于固定长度，窗口重叠用于理解但不重复计证据。长段切分后保留完整覆盖范围和重叠映射。

整理模型输入只有指定原文区间、必要前后文和同主体/属性/时间的旧候选，输出：

~~~json
{
  "facts": [{
    "subject_id": "person-1",
    "predicate": "drink_preference",
    "value": "现在偏好茶",
    "modality": "self_report",
    "valid_from": null,
    "sources": [{"event_id": "e-42", "revision": 1, "span": [0, 14]}]
  }],
  "episode_candidates": [],
  "importance_candidates": [],
  "unresolved": ["有效起点需要从原文语境确定"]
}
~~~

示例偏移仅示意，实际必须按约定的 Unicode code point 偏移验证，不能混用 UTF-16 下标。程序验证 Schema、真实来源、主体、范围、源版本、来源许可、事实/推断类别；模型生成的 source_id 不存在则拒绝。结构验证通过也不能证明抽取语义全对，仍需抽样与评测。

M02 使用输入版本 CAS 提交：输入已更正/删除则丢弃过时输出并重排；重复任务不会生成第二份等价状态。摘要和图更新失败不影响原文入账。

### 6.3 防止“整理漏掉就永远消失”

- 原始文本第一时间建立中文词项检索；未抽取区间仍可查询。
- 每个区间有 coverage 状态；失败和 backlog 显式可见。
- “成功但无事实”保留原因及处理器版本，可以在以后升级时重跑。
- 重要情节进行源覆盖审查：已标注关键断言是否有来源，关键来源是否有表示；审查失败保留原文待复核。
- 定期抽样与用户纠正触发重抽取，检查隐含指代、否定、时间、转述。

覆盖账保障的是“每段都被处理过、可重新处理”，不保证模型理解了所有含义。原文回查与独立评估用于弥补这层不确定性。

### 6.4 新消息尚未整理时，不能继续把旧事实当作已确认当前状态

接收事务同步推进本场景的 pending_reconciliation 水位；这是“有新证据尚未协调”的标记，不需要先用 LLM 猜测该消息是否修改了偏好。默认保守地把该来源可能影响、且有权使用该来源的当前事实视图标为 pending；安全的结构化属性更正可精确缩小范围，否则按场景处理。M06 的可信账号绑定和初始人格卡不属于模型抽取视图，不因闲聊自动变脏。

读取“当前偏好/当前情况”时，必须满足事实头的 reconciled_through 已覆盖本轮快照内全部适用来源、且没有失败缺口。否则触发有输入范围与来源校验的前台优先协调；其提交仍走 M02，后台批次通过幂等键避免重复。优先协调只需确认本次待使用属性，不能伪称整个场景已处理完。

协调超时/失败时，旧值不能以“当前事实”进入 continuity_view 或 selected_memories。包中只提供相关新原文、pending 标记；旧原文若因历史问题确需提供，注明“截至该时的陈述，当前有效性未确认”。无法据新原文回答就保留未知，不强行选一个值。明确指令型纠正也不能仅靠把新旧两句话同时给模型来完成数据库状态更新。

例如刚收到“我现在不喝咖啡了”，即使后台还没运行，旧的“当前喜欢咖啡”也已失去当前事实注入资格。下一轮/新会话同样执行水位检查，因此重启不能跳过这一屏障。代价是首次读取未协调属性可能增加一次前台整理；该成本计入第 17 节并通过实测优化，不能以性能为由取消一致性规则。

## 7 更新、冲突、重要回忆

### 7.1 两条时间轴

valid_from/to 描述事实何时适用；recorded_at 描述系统何时知道。例如今天导入“2022 年住上海”，不能覆盖昨天已确认的“现在住杭州”。时间未知保留未知，不把入库时间当发生时间。

事实链的比较键至少包含 life_id、subject_id、predicate、适用语境。模型只能提出变更，规则检查主体、时间、来源与人工覆盖后决定：

| 新信息 | 处理 |
| --- | --- |
| 同一事实的等价重复 | 增加合法来源引用，不增加独立事件重要度 |
| 同一次事件的补充 | 新版本，保留原版本与新证据 |
| 同类活动在另一时间再发生 | 新情节/事实实例，不能合并成一次 |
| 有明确后续时间的新状态 | 新状态头，旧状态有效期关闭，仍可用于历史查询 |
| 对过去表述的明确纠正 | 建立 correction 关系，撤销错误解释的当前使用资格 |
| 冲突但时间/主体/语境不明 | disputed 并存，不自动选“最新入库”；必要时自然澄清 |
| 模型自己的推测或重述 | interpretation，不作为外部事实覆盖依据 |

人工纠正仍须对应有权限的主体与材料。用户纠正自己的偏好可直接生效；第三方自称纠正主人的身份不具有同等权威。

### 7.2 重要回忆如何长期保留

重要回忆保持原文入口、来源关联、时间和版本，得到更高维护/备份校验优先级；初次相识、明确约定、转折等建立里程碑索引。没有完整历史时使用“已知最早”，不能编造“第一次”。

不实行“时间一到删掉普通原文”的拟人遗忘。时间只影响当前激活和相关候选排序；用户设定保留期限或主动删除除外。冷数据可无损压缩归档，查询索引仍覆盖全时期，需读取时解压；禁止只扫最近固定文件大小却声称搜完一生。

置顶不意味着每轮全文注入。最小身份锚点属于连续性加载；重要往事的详细叙述仍须通过当前相关性判断。明确询问老事时不施加近期性惩罚，也不因“刚说过”拒绝回答。

## 8 检索：怎样避免拿出无用记忆

### 8.1 从当前意图生成受限查询

输入包括当前用户消息、少量本场景最近话语、工作头中的实体指代；不是拿全部历史生成一个巨大 query。

先判定类别：身份/偏好精确问答、当前状态、过去某时、共同经历、跨事件汇总、普通闲聊。规则能处理的 ID/日期/明确引用先处理；指代和模糊时间可用受限模型生成最多 3 个候选查询。查询扩展不能虚构答案或扩大权限。

“她”“那次”无法可靠消解时保留多个假设，检索结果带其假设；没有足够证据就表达不确定。主动联想关闭时不生成纯情绪/主题触发的往事查询，但仍能读取回答必需的事实以及用户明确询问的记忆。

开关沿用既有配置；对没有配置的新部署，本提案暂定主动联想默认关闭，直到用户选择开启。这是设计者的默认值提案，不是用户已确认选择。设置按生命级持久化，未来可加更严格的场景覆盖；关闭立即使在途纯主动联想候选失效，不删除原文，不停用必要事实检索；重新开启不补发停用期间的回忆。

### 8.2 权限先于候选池

M12 给出可信 QueryScope：life_id、当前请求人、场景、允许材料/出站目标、policy_version。模型不能传任意 person_id 或 scope 来获得权限。

每一路检索只在授权材料上取 top-k，禁止先全库 top-k 再仅丢弃违规结果：那既可能泄露存在性，也会使合法结果被挤掉。向量后端必须支持筛选或基于已授权 ID 集精确检索；不支持时按权限分区，不能靠“多取一些”代替正确性。

聚合记忆继承全部来源限制的交集；没有可共同披露的范围则分开表示。涉及 private 来源的摘要不能通过改写变成 public。

### 8.3 多路召回及默认实验预算

| 路径 | 内容 | 首轮候选上限提案 |
| --- | --- | --- |
| 结构化精确查询 | 已绑定主体、属性、事件 ID、当前/历史有效期 | 20 |
| 中文全文 | 原文块、事实、情节标题与标签；一致中文分词 + 字符二元组补充 | 40 |
| 语义向量 | 原文块与派生表示的独立命名空间；中文语义改写 | 40 |
| 情节/时间导航 | 指定时期、开放情节、显式回指 | 20 |

这是调优起点，不是经测试的最优数值。同源重复按事件/事实链聚合；合并池上限 120。精确指向的证据不因重复摘要数量少被淹没。全库索引覆盖历史，不按年份截断；查询成本受候选和分页预算约束。

关键词需要真实中文测试。默认实现选择可版本化的本地中文分词器，辅以字符二元组和专名/数字精确通道；FTS 不具备该能力则启动诊断失败，不能返回“没有记忆”。embedding 选择依据中文同义、否定、人物、时间测试和本机/配置端点预算，模型/维度固定到 manifest，不能用词项 hash 冒充语义模型。

向量持久索引建议从 SQLite 内嵌适配器实现；小数据量可只对授权候选做精确余弦扫描。是否使用扩展/ANN 由规模压测决定，公开统一 VectorIndex 接口。没有合格语义后端时报告 lexical_only 或 semantic_failed；这可以运行基础模式，但不能宣称完整语义检索验收通过。

### 8.4 融合不等于采用

先用 RRF 等秩融合把不同分数尺度合成排序，不将 RRF/余弦相似度解释成可信度。随后对最多 30 个候选做重排与相关性判定：

1. 这条材料是否真的涉及当前主体、事件、时间和问题？
2. 是直接证据、必要背景，还是只有关键词/情绪相似？
3. 状态是否有效；冲突是否已经表示；是否应读原文？
4. 是否与已选材料重复；能否补齐问题所需的另一证据？

相关性输出带类别 direct/supporting/unrelated/uncertain 及证据引用。正式阈值必须在留出的中文负样本集校准；默认只自动采用 direct 和必要 supporting。uncertain 不硬塞进回复，可触发有限回查；没有可靠项允许返回空。

重排器首选可本地运行的已评测中文 reranker；尚未选型时可用固定模型配置的结构化相关性裁判作候选实现，必须计入延迟/成本。裁判输出不是安全边界，ID/权限/时间仍由程序核验。

通过相关性门槛后，再考虑重要度、时效性、多样性和近期提及抑制。明确历史问答不加时效衰减；主动联想可以抑制近期反复提过的同一故事。不能为了凑满 4,000 tokens 加入无关内容。

### 8.5 有界关联与原文回查

当直接证据不足时，沿已授权的 episode_members 或有类型 memory_links 扩展 1 跳，最多 10 个候选，再过相同相关性检查。图的高连接度不能构成相关证据，图损坏可以关闭该路；权限判定失败必须停止读取。

回答日期、原话、约定内容、状态变化或冲突时，必须优先展开原文及必要相邻话语。普通偏好应用可以用已验证事实；情节回忆可先用短摘要，回答涉及细节时补证据。

读工具只有 search_memory 和 read_evidence 两类。每轮最多 2 次追加读取批次，累计新增材料预算默认 4,000 tokens，与上下文总预算共同约束。数量不够时返回 partial/truncated 和可继续入口，不能把预算截断误报成“没有更多”。跨多年“全部列出”必须分页或作为有覆盖清单的长任务。

模型不是唯一检索发起者：新会话连续性与首轮召回由程序执行；否则模型不知道自己不知道什么，可能从不调用记忆工具。

## 9 索引一致性与恢复读取

原文/事实提交和 index_outbox 在同一事务内；全文索引能事务更新就同步更新，向量按 outbox 异步处理。每个索引项带 source_id/version、policy标签、index_generation。

索引查询返回 ID 后必须到权威记录复核当前版本、删除标记、范围和来源可用性。向量项存在不代表源事实仍有效；索引超前/落后不允许读取失效数据。

索引维护用“连续覆盖水位 + 失败缺口集合”，不能只记最大 seq。落后区间及失败缺口通过权威全文通道补查；语义未覆盖时显式降级。对紧邻的新对话直接读取 raw tail，避免等待异步抽取。

embedding 模型变更创建新命名空间，不能混合不同维度/模型分数。重建从固定来源快照开始，追赶增量，校验覆盖后原子切换 generation；旧索引可回滚，但删除策略的 epoch 不能回滚。缓存键包含 life/scope/query、依赖版本、policy_version、index_generation 和 restore_generation。

定期健康检查：原文与引用的完整性、coverage backlog、FTS 可用性、索引缺口、失败任务、超期租约、备份年龄、删除待处理项。原文健康但索引坏时重建索引，不能新建空白生命。

## 10 上下文怎么组装

### 10.1 ContextPacket 是每轮的明确交付物

M09 不给大肥鱼一个无边界的“记忆库文本”，而是给一个带来源、状态和预算的包：

~~~text
ContextPacket
  turn_id / input_event_id / life_id / conversation_id
  policy_version / restore_generation / snapshot_version
  persona_version / trusted_instructions
  continuity_view                 对方是谁、连续关系依据、开放事项
  current_state                   来自 M05/M06/M08 的授权状态引用
  working_summary                 已覆盖区间与未确定事项
  recent_messages                 按时间的真实原文，保留说话者
  selected_memories[]              事实/经历、有效时间、类别与引用
  evidence_excerpts[]              原文版本、偏移、时间、必要邻文
  retrieval_status                found / none / partial / unavailable
  missing_information[]           缺口，不是模型自行补全的邀请
  pending_reconciliation[]        尚未协调的来源区间/属性，旧值不可宣称为当前
  dependency_manifest             每项源版本与许可范围
  budget_manifest                 每部分实测 token 数
  input_message                   当前用户原文
~~~

Packet 本体不包含密钥。用于审计的持久副本默认只存材料 ID/版本、选择理由、hash、模型参数与 token 清单；若保存渲染正文，它也继承源材料保留/删除规则，不能成为遗漏的第二套聊天库。

### 10.2 预算算法

不能把用户提到的“1M”写成永远可用的配置常量。M14 读取实际模型/路由允许的上下文上限，并对完整最终请求计数。

~~~text
B_input = min(场景配置的输入目标,
              模型有效窗口 - 最大输出预留 - 适用的推理预留 - 安全余量)

成本 = 系统指令 + 人格 + 记忆包 + 近期消息 + 当前消息
     + 工具定义 + 工具调用/结果 + 宿主包装
要求：成本 <= B_input
~~~

推理 token 是否占窗口依模型协议处理，不能重复扣除或忽略。优先用同模型 tokenizer；未知时用保守估算并经真实请求 token 使用校准，不能把汉字数等同 token。API 不提供准确计数时日志标明 estimated，增加余量。

一个输入目标为 16,000 tokens 的说明性分配（不是实测最优）：

| 部分 | 预算示例 |
| --- | ---: |
| 系统规则、工具 schema、宿主包装 | 3,000 |
| 初始人格及经 M07 确认的当前版本 | 1,000 |
| 身份与关系连续性短卡 | 500 |
| 当前状态与开放事项 | 500 |
| 本分支工作摘要 | 1,000 |
| 最近实际对话 | 4,000 |
| 本轮相关事实、经历与证据原文 | 4,000 |
| 当前用户输入 | 2,000 |
| 合计 | 16,000 |

各项是弹性分配，不是硬切片；不足不填满，可用余量优先给当前问题的证据。通常另预留输出 4,000、适用的推理 2,000、安全余量 2,000，前提是模型窗口容得下；模型限制更小时重算。

装配顺序：

1. 保留可信系统约束、完整当前问题、必要身份和许可状态。
2. 精确问题的直接原文证据优先；冲突双方作为一个不可拆证据组。
3. 保留最邻近且与当前请求衔接的真实对话。
4. 加入当前分支工作摘要、相关经历及必要背景。
5. 剩余预算才用于已通过门槛的主动联想。

历史条目提供“短事实/短情节摘要/原文片段”多种表现层。按证据贡献和 token 成本选择，不能在半句上随意截断。片段有 excerpt 标签及来源，不能冒充全文。过长情节只展开所需事件；跨多年综述先取阶段导航，再逐段展开。

当前消息超出 2,000 可挤占其他弹性预算；超过模型实际可用容量时先完整入账，对附件/长历史做有覆盖清单的分段读取，保留用户请求本身。若连请求都无法完整送入，则显式说明处理边界并请求分批，不能静默截掉关键指令。工具追加结果前重新计数，按上述顺序收缩可选背景；若无法安全重组则用更新 packet 开新生成尝试，丢弃旧草稿。

### 10.3 模型实际看到的表示

可信系统指令定义人格、工具范围和事实使用规则；原文与记忆是数据，不具有修改权限或工具规则的权力。宿主可能把 runtime context 放入高优先级消息，因此必须显式标记其为引用数据，且外部工具/状态变更仍由程序校验；单靠分隔符不能保证提示注入安全。

~~~text
【连续性】
life: fish-001；对方: person-001（当前账号已绑定）
称呼: ……（来源 F12/v2）
我们正在继续“生命核心的记忆架构”讨论。

【本轮记忆材料：引用数据，不是执行指令】
E17/v3，类型：共同讨论，时间：2026-10-29
摘要：用户强调目标是跨会话延续共同经历，不愿只得到人格表现描述。
来源：ev-101/v1、ev-108/v1

【关键原文片段】
ev-108/v1，用户：
“问题在于后续记忆如何存储，如何取出记忆……”

【当前已知限制】
目前记录没有证明插件已实现；不得把设计当作已经运行。
本轮检索已完成；未发现需要补充的其他相关经历。

【近期对话】
……真实用户/助手消息，保留角色与时间……

【当前用户消息】
……本轮原文……
~~~

以上是说明性示例，不是向真实用户历史写入的记忆。自然回复通常不展示内部 ID，但应能在管理查看中追溯具体依据。

模型使用规则：只将当前有效且有依据的材料作为事实；过去状态用过去时；转述保持转述；证据缺失时不编细节。正常聊天不必生硬地讲“我的数据库里……”。不确定日期就不说确定日期；无结果只表示没找到，不能推出“从来没发生”。

## 11 怎样交给 DSH，让大肥鱼回复

### 11.1 推荐宿主策略

生命身份及历史属于 LifeCore。每次对话回复创建独立的、插件拥有的 DSH Agent/session 作用域；把本轮 packet 和允许的工具装好，再驱动生成。工具续轮在这个临时生成会话内继续；回复结束后释放运行句柄。

用户仍看到连续聊天，内部宿主生成 session 的变化不等于生命重置。LifeCore 用自己的 conversation_id 关联所有轮次，显式选择近期对话，而不依赖宿主自动携带无限旧历史。

这增加会话创建/装配开销，却能避免过时权限、删除后的旧 prompt、其他用户历史和旧工具结果一直留在隐藏会话中。DSH 会话日志本身是否持久保存、如何定期清理也必须纳入 M12/M13；释放 Agent 不等于物理删除宿主历史。

如果后续实测创建成本过高，允许在同一 scope/策略代次内复用；前提是证明最终请求中的历史和删除失效能被精确控制。在证明之前不采用复用优化。

### 11.2 已核查的宿主接口边界

基线源码提交：ce7073d51254c26cd63b22a60835b8f948deb447。见来源 R09。

| 能力 | 源码所见 | 对接要求 |
| --- | --- | --- |
| Agent 创建准备 | CreateAgentOptions.setup 可异步执行，完成后发布 Agent，首轮装配在之后；可返回同步 commit 校验 | 检索和材料准备放驱动前；创建时安装作用域资源 |
| 动态上下文 | systemPrompt.context 注册 text 字符串或同步 provider；支持 required、interpolate | 不在同步 text provider 内做异步检索；注册已准备好的材料 |
| 作用域 | 通过 Agent 的 ctx 安装 prompt/工具；全局与局部注册有继承和遮蔽规则 | 不全局注入某个人的私人记忆 |
| 工具限制 | scoped tools.restrict；全局限制不是等价方案 | 只开放授权工具，不能默认继承宿主全部能力 |
| 会话日志 | 提交事件通知与持久/flush 边界分开，监听失败不回滚已提交记录 | 不能仅靠易丢的监听回调摄入，需要重放/对账路径 |
| 生命周期 | create/resume 返回有 dispose 的拥有者句柄 | 插件停止、取消及超时后停止/回收生成；实际日志清理另做 |

上表是源码证据，不是编译/联调完成声明。以下仍是发布前必须做的兼容性探针：实际 Agent 驱动与终止结果映射；平台消息进入 LifeCore 后只触发一个回复者；最终 provider request 的历史/角色/工具清单；日志删除/保留能力；取消是否停止后续输出；模型切换/路由回退是否仍满足预算和出站许可。

任何关键能力不满足，应报告不兼容并调整适配器，不能回落到“随便找一个旧会话继续聊”。暂时无法清除 DSH 历史的版本只能声明删除限制，不得宣称全链路物理删除完成。

### 11.3 内部接口与伪代码

以下 HostAdapter 等名称是 LifeCore 设计接口，不是声称 DSH 已存在同名 API：

~~~typescript
interface HostAdapter {
  capabilities(): Promise<HostCapabilities>
  runPreparedTurn(input: {
    turnId: string
    packet: ContextPacket
    tools: ScopedReadTools
    signal: AbortSignal
  }): Promise<ReplyDraft>
}

async function respond(envelope: IncomingEnvelope) {
  const accepted = await coordinator.acceptEvent(envelope) // 原文+整理/回复任务+turn占位同一事务
  if (accepted.duplicate) return existingTurnState(accepted.eventId)
  const turn = await coordinator.startTurn(accepted.eventId) // 领取已持久化占位；崩溃后由dispatcher恢复
  const scope = await privacy.authorizeReadAndModelEgress(turn)
  const snapshot = await queryService.readSnapshot(scope)
  const recall = await memory.retrieve(turn.query, scope, snapshot)
  const packet = await contextBuilder.build(turn, snapshot, recall)
  await coordinator.recordPacketManifest(packet)
  const draft = await host.runPreparedTurn({
    turnId: turn.id, packet,
    tools: scopedMemoryTools(scope, turn),
    signal: turn.signal
  })
  await coordinator.validateDraftDependencies(turn, packet, draft)
  const action = await coordinator.commitOutboundDraft(turn, draft)
  const receipt = await delivery.sendAndRecord(action)
  await coordinator.acceptDeliveryReceipt(receipt)
}
~~~

真实实现必须把失败分支和状态持久化，不能把上述函数的连续执行当作跨网络事务。

伪代码把接收与领取顺序写在一起便于阅读；真实执行由持久 dispatcher 驱动，重复事件返回不影响原有 pending job 的重启恢复。查询服务在建立事实快照前执行第 6.4 节的协调屏障。

### 11.4 回复后的闭环

ReplyDraft 包含回复正文、使用的证据 ID（审计用途）、不确定项和可选记忆/行动候选；不收集隐藏思维链。模型自报引用不能当作正确证明，程序验证 ID/状态，显式回忆问题可增加受限的依据检查，仍需评估其误判。

M02 检查当前轮未取消、主体/场景/源版本仍有效、关系/承诺状态依赖未过期；旧任务的结果不能覆盖新一轮。然后 M11 写待发送记录并执行发送：

~~~text
prepared → sending → confirmed
                  ↘ failed_retryable / failed_final
                  ↘ outcome_unknown → reconcile
~~~

生成成功只是草稿；平台确认或可核实的发送结果后，才记为已向对方说过。unknown 状态保留候选和证据，不自动重发；支持幂等键的平台才可按其保证重试。没有核实接口时保持未知，不能假装成功。

正式默认先缓冲完整回复，经依赖检查再发送；如要流式输出必须接受已展示内容不可撤回的事实，并单独设计/测试。用户看到的“记住了”只能在相关原文事务成功后出现；只完成原文保存时不能宣称事实整理和永久容灾都完成。

已发送回复重新成为账本事件，供之后理解交流过程。它能证明“她说过这句话”，不能证明“她描述的外部行动已经发生”；行动结果以实际回执为准。反复从自己的回复抽取同一说法不增加事实可信度。

## 12 新会话如何认识你：一个完整示例

假设某次你说：“我现在喝茶了，咖啡最近喝得少。我们上次讨论的记忆方案还没定。”

1. 原文先入账；保留“最近”“少”这种限定，不能过度概括为“永远不喝咖啡”。
2. 新偏好建立有时间语境的事实候选；过去喜欢咖啡的记录仍保留。
3. “记忆方案未定”关联已有讨论情节与未完事项，不能自动标成已完成。
4. 几天后新开 DSH 会话，账号绑定仍指向同一 person_id。系统载入人格、称呼、合法关系依据及讨论入口。
5. 你问“上次我们说到哪了？”：工作头解析“上次”的分支，全文/情节检索找到方案讨论，读取最后决定与未决原文。
6. 预算内只放该讨论所需材料；喝茶偏好虽重要但对这次问题无帮助，不放进详细回忆区。
7. 大肥鱼据此接着回答未决架构问题，不需要你重新介绍自己。

如果你问“我以前是不是喜欢咖啡？”就检索历史状态链；问“现在给我推荐什么饮料？”则用当前偏好。问“我们第一次见面你穿什么？”但从未发生过真实线下见面，系统不能把初次聊天扩写成虚构现实场景。

这个例子说明“持续认识”和“每次挑对回忆”是两条共同工作的路径，不能仅用一个向量 top-k 替代。

## 13 并发、取消与故障

同一 conversation_id 的回复按接收序列排队，合并只允许显式批处理并保留消息映射。不同场景可并发检索/生成；数据库写事务由 M02/M13 单写队列串行处理，不能持锁等待模型。

turn 状态：accepted → preparing → generating → ready_to_send → delivering → finished；另有 cancelled、failed、delivery_unknown。状态变更与待办事务提交。每次生成捕获依赖版本；不因无关的新事件重算全局，只在已用依赖/权限/当前场景头发生实质变化时作废或重做。

| 故障 | 必须发生的行为 |
| --- | --- |
| 原文事务失败/磁盘满 | 不返回 accepted，不说记住了；停止静默接收，使用宿主可重放记录追赶；没有来源重放则明确可能缺口 |
| 抽取模型不可用 | 原文继续保存及全文可查；coverage 留 pending/failed，不用失败摘要覆盖旧版本 |
| 向量/reranker 不可用 | 标记降级；精确/全文路径可继续，不能将错误伪装为“没有相关记忆” |
| 权限/身份状态不可读 | 不读取私人长期材料；无法确定基本出站目标则不发送 |
| 进程在提交后退出 | 从持久任务恢复；幂等键阻止重复抽取/重复成长 |
| 生成完未发送时退出 | 可以恢复草稿但先重校依赖；不能假定对方已经看到 |
| 发送中失联 | outcome_unknown，核对回执；不盲目重发 |
| 删除发生在生成中 | 取消受影响轮次，撤销包/缓存/工具能力；重建后生成 |
| 宿主旧回调晚到 | 检查 turn_id/代次/取消状态，忽略过时结果 |
| 索引损坏 | 从权威记录重建，保持生命 ID 与历史不变 |
| 数据库损坏 | 停止写入并保全损坏副本，从已验证备份恢复；不自动“重新出生” |
| DSH 停止后恢复 | 恢复状态与待办，不补造离线生活，不补发未知历史动作 |

## 14 “不会缺失”到底能保证到哪一步

必须分开四件事：

| 层次 | 工程承诺 | 不能承诺的部分 |
| --- | --- | --- |
| 收到后保存 | 在本机存储正确、WAL+FULL 配置生效等前提下，已确认提交的事件可在崩溃后恢复；幂等重放补齐可重放来源 | 平台从未送到、无重放接口的漏回调、磁盘物理损毁、违规/主动删除内容 |
| 整理覆盖 | 所有获准区间有处理状态；所有派生条目有来源；失败可重试，原文可重建 | LLM 每次都完整理解所有含义 |
| 检索 | 历史索引覆盖、中文多路召回、时间/身份过滤、缺口可观测、原文回查 | 任意模糊提问百分之百找到想要的那件事 |
| 回答 | 提供可核实依据、冲突与缺口；外部状态受程序保护；评估支持率/编造率 | 模型绝不误解或幻觉 |

持久性采用 SQLite WAL + synchronous=FULL、外键约束、短事务、本地可靠文件系统；启动时读取实际 PRAGMA 值验证，不能只发出设置语句。日志配置依据 E01/E02，不把 FULL 描述成对所有硬件故障的保证。

默认备份提案：每小时一致性本地快照，保留 24 个小时版本及 30 个每日版本；附件按快照引用建立 manifest、hash 和完成标记；至少每日校验快照，每周做一次隔离恢复演练。使用 Online Backup API 或经验证的等价机制，不只复制活动 db 文件。

小时备份意味着本地回滚的目标 RPO 最多一小时，只有备份按时成功才成立；同盘备份不能抵抗整盘故障。真正容灾需要用户配置另一个故障域的加密备份，显示最后成功时间与实际 RPO。不能把未配置的异机备份算成已有保护，也不私自上传数据。

容量达到预警线时提示扩容/清理选项；满盘硬失败而非静默淘汰历史。备份轮换可以删除过期备份，不等于删除权威历史。多年原文可按时间无损归档，核心身份/事实头/索引仍在线；归档必须仍可校验与回查。

## 15 删除、更正与恢复不能互相打架

用户删除目标可为某条记忆表达、某段原始经历或全部主体资料；界面与接口必须明确范围。“删除派生条目但保留原文”如果不增加抑制规则，下次抽取会再生。因此删除表达时也存来源/断言抑制规则，直到用户撤销该规则。

完整清除流程：

1. M12 校验权限，按下述删除账本协议先持久化删除意图；再创建主库删除事务，写 tombstone 和新的 deletion_epoch，阻止所有新读取。
2. 通过 source_deps 找到事实、情节表达、摘要、连续性视图、关联、向量、全文索引、缓存、packet、待发送草稿及宿主会话等后代。
3. 取消正在使用这些来源的任务/生成；清理或重新构建受影响派生材料。多来源表示先整体失效，再用剩余合法来源重建，不能直接删 source_id 留原句。
4. 记录各存储位置的清除状态。模型服务已收到的内容不能由本机撤回，按服务保留机制说明；本地日志、备份和介质物理残留分别说明。
5. 管理审计只留必要 ID/操作时间，不留被删除正文。

恢复备份前，必须取得不随该备份一起回滚的最新 deletion ledger/策略代次（独立持久位置并随容灾体系备份），先应用删除与撤销，再开放读取。若只剩旧备份且无法证明 ledger 是最新的，恢复到隔离待核验模式，不直接让大肥鱼使用旧私人材料。

### 15.1 删除账本的提交与恢复协议

这是主库之外的小型持久账本，仅保存删除 ID、目标 ID/断言抑制引用、单调序号、前记录 hash、校验码和操作范围，不保存被删除正文。存放在独立于数据库恢复目录的位置，由同一 M02 写入者串行管理，普通备份恢复不得覆盖它。

1. 协调器先暂停受影响范围的新读/出站，生成唯一 deletion_id。向账本追加完整 DeleteIntent(seq, prev_hash, targets)，刷新到持久介质；新建/轮换文件必须使用经验证的原子替换及同步协议。完整且同步成功的记录就是删除意图的提交点，之后不允许被主库回滚取消。
2. 在主库事务中幂等应用 tombstone、策略失效、后代清除任务和 applied_delete_seq；同一 deletion_id 重放无副作用。此事务完成且现有相关出站任务已被取消/阻断后，才确认“已停止使用”。物理清理另报进度，不能提前确认完成。
3. 若在步骤 1 后、步骤 2 前崩溃，启动先扫描独立账本、校验序号/hash 链，重放大于 applied_delete_seq 的全部完整记录，再开放任何记忆读取。未完成尾记录不视为已提交删除；若出现中段损坏或无法确定尾部状态则隔离处理。步骤 1 未确认成功时不得对用户确认删除。
4. 每个备份 manifest 记录该快照的 applied_delete_seq/hash。恢复时读取独立账本的当前已验证 head，从备份水位重放到 head；head 落后于备份记录、链断裂或谱系不匹配都拒绝开放。独立账本轮换必须保留可衔接的累计 tombstone 检查点。
5. 本机普通回滚的最新性依据是仍存活且未被恢复操作覆盖的独立账本。容灾恢复到新设备时，旧快照自身无法证明没有后续删除；必须使用独立故障域持续维护的删除 head/账本副本。若部署承诺异机恢复后不复活，则删除确认还必须等待该副本持久确认，并以单调 head 更新防止旧副本覆盖新副本。无法取得这份最新性证据时，只能隔离恢复。

该协议不需要新增生命服务器；独立文件/已配置的备份目标即可实现，但没有异机副本时必须如实限定为本机恢复保障。不能用一个与数据库一起回滚的“已同步=true”字段证明账本最新。任何人工恢复旧账本的操作都使最新性证明失效，进入隔离核验。

本地查询不可见可以立即实现，旧备份物理清除有保留窗口；若要求更强清除，可采用分对象加密和销毁对象密钥，但密钥副本/备份同样要纳入设计。不得承诺普通 SQLite DELETE 能擦除 SSD 上每一处物理残留。

## 16 模块接口与职责落点

| 接口 | 调用方向 | 结果及失败语义 |
| --- | --- | --- |
| acceptEvent(envelope) | M10/M14 → M02 → M03/M13 | event_id、accepted/duplicate、提交位置；失败不确认 |
| authorizeQuery(turn, target) | M09 → M12 | 可信 QueryScope 或 denied/unavailable |
| readContinuity(scope) | 应用查询 → M06/M08/M04/M13 | 来源版本化视图；区分未知主体与服务故障 |
| retrieve(query, scope, budget) | M09 → M04规则/应用查询 → M13 | 候选、证据、coverage、降级、筛除理由；不直接调用外部模型 |
| evaluateCandidates(task) | M02/应用服务 → M09 → M14 | 抽取/重排候选，不提交记忆状态 |
| commitMemoryProposal(proposal, deps) | M02 → M04/M03/M12/M13 | applied/stale/rejected，带验证原因 |
| buildContext(input) | M09 | ContextPacket/预算错误/材料不可用 |
| runPreparedTurn(packet, tools) | M09 → M14 | ReplyDraft 或超时/取消/宿主不兼容 |
| commitOutboundDraft / receipt | M02 ↔ M11/M10 | 明确发送状态，未知保持未知 |
| erase / restore | 管理入口 → M12/M02/M13 | 全链路进度、不可逆范围和未完成项 |

M04 的纯规则只接收材料/候选，不直接调用数据库或模型；表格中的检索执行由应用查询服务编排 M13，重排调用由 M09/M14 提供能力。这样“记忆逻辑”和外部实现可以独立测试/替换，仍符合原分层。

## 17 成本、延迟和规模策略

每次普通聊天的基础预算：1 次回复模型调用；中文全文/结构化本地查询；1 次查询 embedding（可缓存）；最多 1 批重排。尚未协调的当前属性读取另计前台优先协调。指代解析能由本地规则/已有工作头完成时不额外调模型；复杂问题才启用查询扩展与最多 2 次补查。

后台：每批原文做 1 次结构化整理，必要的新旧候选协调另计；不在每轮全量重写人生摘要。摘要、embedding、失败重试、重排、工具续轮都计入费用账本，不只统计最后一次回复。

默认资源提案：最多 2 个并发前台生成、1 个后台模型任务；同场景串行；用户显式纠正优先；后台不得无限挤占前台。具体并发可按实际机器和端点配额调整。长时间积压应降速和提示覆盖状态，不能为了清空队列跳过重要区间。

性能目标不是“1M 上下文越满越好”，而是用较小且相关的包稳定回答。规模测试分别覆盖 1 万、10 万、100 万事件；数据量增长影响磁盘/索引与检索时间，不应让每轮 prompt 与人生长度线性增长。延迟/费用必须在实际运行环境报告，本文不虚构毫秒数字。

## 18 验证与交付顺序

具体数据、对照、故障测试和门槛见 [验收方案](M04-M09-memory-evaluation.md)。可分三段实施，但只在各阶段条件满足后声明相应能力：

1. **持久连续性闭环**：原文事务、幂等/重放、稳定身份、场景隔离、FTS、版本/纠正、备份恢复、ContextPacket、DSH 唯一回复路径。证明新会话接续，且故障不静默丢已提交文本。
2. **完整语义记忆**：事实与情节抽取、覆盖账、中文 embedding 与重排、时间事实链、有限原文回查、删除传播。通过统一中文基准，才能称完整目标架构已落地。
3. **长期质量优化**：轻量关联扩展、分层时间导航、个性化激活、多规模压测；每项必须用消融证明增益，不能以复杂度代替效果。

第一段可以真实使用基础记忆，但不能包装成第二段的效果。此次交付到设计/研究文档；上述实施阶段均未完成。

## 19 方案的核心结论

“完整的一生”在工程上对应：一份可恢复的经历记录、一套带来源与时间的理解，以及每次对话中正确使用这些材料的过程。

本方案把最不可逆的损失挡在摄入和保存阶段，把模型整理变成可纠正、可重做的派生过程，把无关回忆挡在相关性和预算门槛外，再由 DSH 将明确的上下文交给大肥鱼。它能给出可验证的连续性与持久性保障；是否达到足够自然、准确的长期陪伴，必须由真实模型和长期测试结果回答。
