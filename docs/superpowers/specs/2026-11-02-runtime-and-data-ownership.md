# LifeCore 设计梳理 02：总体职责、执行场景与数据归属

日期：2026-11-02（Asia/Shanghai）。状态：P1 总体设计建议稿，待用户核对；不授权开发或安装。

承接：[01 基线、职责与待决事项](2026-11-02-design-baseline-and-responsibilities.md)、[插件候选证据](../../architecture/references/2026-11-02-dsh-plugin-reuse.md)。本稿细化 R01/R02，并为 R03–R06 提供接口约束；记忆后端、物理存储、编程语言、首版范围及数值预算仍未定案。

后续细化：[03 共同契约](2026-11-02-common-contracts.md)及[故障验收表](2026-11-02-common-contracts-acceptance.md)已形成出生、事件接收、执行绑定、授权、动作回执和恢复的完整流程建议；接口与组件仍待核对，未实施。

用户本轮“继续”授权进一步梳理，不等于逐项批准本文建议。文中“必须”表示本方案成立所需的设计约束，不能据此宣称已有产品实现。

## 1 这次要解决什么

目标：大肥鱼具有同一身份、关系与成长历史，通过 DSH 和不同插件获得能力；增加一个视频、搜索或记忆插件时，不需要重建生命，也不额外产生不受协调的自主回复者。

必须分别说清三个问题：谁决定做什么，谁执行具体步骤，谁保存和判定最终结果。一个模块的责任可以由复用组件实现，但责任不能因为“插件会处理”而消失。

本轮不选择具体检索算法，不确定情绪/人格公式，不编写开发任务或接口代码。对尚需实测的宿主行为只提出验证条件。

## 2 方案比较与推荐

总体路线沿用 01 中的建议 C：LifeCore 统一生命规则，DSH 提供 Agent 执行，能力插件提供可控的工具或服务。其替代路线为主要自研运行系统，以及并用多个完整生活插件；前者维护面大，后者缺少统一状态与调度契约。

执行场景还有三种组织方式：

| 方式 | 收益 | 代价 | 本稿建议 |
| --- | --- | --- | --- |
| 所有活动共用一个长期 Agent/session | 结构直观，最近交流容易连续 | 不同人和平台历史混杂，工作权限难隔离，视频任务容易挤占聊天 | 不采用为默认组织 |
| 每条消息都新建 Agent，完全重建上下文 | 每轮边界明确 | 需要自建更多工作记忆/恢复流程，插件的会话钩子可能失去连续性 | 留给特定短任务，不作为全部交互默认 |
| 一个生命，按场景维护连续工作上下文，按任务配置执行 Agent | 可复用宿主连续会话、工具循环和恢复，同时限制信息与能力范围 | 需持久场景映射和受控交接 | 推荐；不等于一个场景永远只有一个物理 session |

推荐的核心：**共享身份与经过授权的生命状态；按场景提供上下文；按任务授予能力；按回执确认结果。**

## 3 三层职责与不应重复开发的部分

| 层 | 拥有的决定 | 执行或复用的工作 | 不应替其他层做的决定 |
| --- | --- | --- | --- |
| LifeCore 生命规则 | 身份、关系/人格版本、活动优先级、场景授权、记忆含义、完成标准 | M01–M13 的领域规则可部分复用；M14/M15 负责接入和管理 | 不重写 DSH 的通用模型工具循环，不直接维护每个平台协议全部实现 |
| DSH 执行运行时 | 已准入 Agent 的模型步骤、工具执行和会话记录 | 模型路由、Agent 作用域、工具注册、提示词装配、运行取消、持久会话后端、配置入口 | 不把 session 当 life_id，不自行判定某段工具结果就是正式成长或平台已送达 |
| 能力插件 | 在已约定范围内完成具体能力 | 视频发现/提取/播放、平台传输、记忆提炼/检索、语音等 | 不私自扩大用户授权、不维护另一份正式人格或绕过总暂停继续生活 |

M14 是 LifeCore 与宿主能力的连接层，M10 是平台/媒体语义转换层；不另造第四套运行框架。优先使用插件公开接口，适配仅补来源、权限、状态和回执差异。

### 3.1 调度责任分成三件具体的事

- **M08 决定生活上的安排**：当前做什么、为何打断、是否继续、哪个承诺更紧急。模型可协助提出选择，程序检查允许范围。
- **M02 决定业务状态的流转**：事件是否接收、哪个场景处理、版本是否仍有效、哪个结果可提交，以及崩溃后哪些工作待核对。
- **DSH 决定获准执行中的技术步骤**：把本轮交给模型，执行允许的工具，接收结果，再继续下一步。

三者不得分别重新调度同一笔发送或创建三份待办。平台插件的独立定时器只有能作为 M08 的受管执行器、接收启停和输出状态时才能用于正式生活；否则关闭它，只复用工具，或者将该插件排除出此运行组合。

### 3.2 已有能力应该保留在原处

优先直接复用 DSH 的模型适配、工具参数验证、执行循环、会话历史与管理入口；优先直接复用插件的内容采集、格式处理、检索算法与登录页面。LifeCore 不因为需要统一体验就复制一套相同设置和数据库。

确需适配时先写出无法通过配置满足的差距。工具插件只要满足接入契约，就可以新增能力；带自动注入、后台任务或独立 Agent 的插件需多核对这些入口，不能仅凭工具名单认定已受控。

## 4 同一生命、多种场景的逻辑对象

这些名称表达业务含义，不是已冻结代码字段。不能把所有对象都映射为一个“会话 ID”。

| 对象 | 含义与寿命 | 权威/恢复方式 |
| --- | --- | --- |
| 生命 | 唯一正式身份及出生来源，跨平台/模型/session 持续 | M01/M07 管理；加载失败进入恢复，不新建替代生命 |
| 人物与账号绑定 | 谁在说话，平台账号如何对应人物 | M06 核实；昵称相同不自动绑定，绑定不自动授权共享历史 |
| 场景 | 平台、接入账号、对话方/群/频道及隐私边界 | M10/M12 确定；试聊、正式私聊、群聊、工作分别标识 |
| 对话分支 | 同一场景中的连续主题或任务线 | M02/M09 管理；默认按场景连续，确有多条主题时才分支 |
| 工作段 | 对话分支在当前上下文中处理的材料区间 | M09 定义覆盖与交接；阈值/压缩算法留到 P3 |
| 活动/任务 | 看视频、完成报告、待履行承诺等可跨回合事项 | M08 管理状态、资源与检查点，不依赖某个 Agent 常驻 |
| 执行绑定 | 场景或任务到当前 DSH Agent/session、能力配置和代次的映射 | M14 经 M02/M13 持久登记；重建不改生命身份 |
| 执行尝试与动作 | 某次模型/工具尝试，以及可能影响外部的具体操作 | DSH 记录执行轨迹；M11 保存动作、授权绑定和实际回执 |

DSH 当前实现可能让一个 Agent 与其 session 使用同一标识；LifeCore 仍区分“当前执行实例”与“持久执行历史”的用途，不要求修改宿主。session 更换、恢复或工具变化必须更新绑定，不能凭名称猜测哪个 Agent 属于大肥鱼。

正式 LifeCore 场景使用受控 DSH 配置/作用域，普通用户在 DSH 中的编程聊天不自动加入生命经历。独立配置是否需要单独宿主进程，取决于全局插件能否在目标版本被可靠限制；配置隔离不是进程安全沙箱。

## 5 场景与执行组织建议

| 场景/任务 | 默认上下文来源 | 执行组织 | 权限与输出 |
| --- | --- | --- | --- |
| 出生试聊 | 当前草案、该试聊历史、用户选定测试资料 | 按草案修订隔离的执行绑定 | 无正式社交外发；不能自动提炼到正式记忆空间 |
| 正式 QQ 私聊 | 同一生命当前人格、本对话及获准回忆、可分享的活动快照 | 每个可信场景/分支维持连续绑定；按需创建或恢复 | 仅当前许可的社交/读取能力；QQ 回复经 M11 发送 |
| QQ 群或其他平台 | 同一身份的可公开部分、该场景历史和获准关系信息 | 与私聊分开；平台进入交付范围后才启用 | 不继承主人私聊、管理权或全量活动内容 |
| 看视频等生活活动 | 当前兴趣与任务目标、目标站点内容、该活动检查点 | 按活动分配执行绑定；播放器持续运行不代表模型持续推理 | 提供该活动需要的能力；分享是另一个需核对目的地的动作 |
| 主人交办工作 | 明确任务、所需资料、限定目录及必要身份风格 | 按任务配置独立执行绑定；可暂停/恢复 | 工具和交付对象按任务授权，社交线程不自动获得同等工具 |
| 记忆整理/反思 | 指定来源区间、允许场景与版本 | 后台任务绑定；不对外扮演另一个生命 | 输出派生候选或受约束更新，不发社交消息，不自行改权限 |
| 管理页面 | 经过认证的状态查询与管理命令 | 普通查询不需创建聊天 Agent；需模型帮助时另开受限任务 | 管理登录和社交身份分开；操作通过模块规则提交 |

相同场景/分支默认只有一个能提交新回复的活跃处理序列。新的消息先持久排队；是否作为下一回合或明确打断当前回合由场景规则决定，不能直接给两个 Agent 各喂一遍。具体合并/插话算法在 M02/M09 细化。

不同场景可以并行执行，但共同资源（同一播放器、同一外发账号、模型预算）需协调。单生命不要求全局只允许一个模型调用；并发上限也不沿用旧草稿数字作为确认值。

### 5.1 创建、恢复与轮换

1. M02 查找持久场景或任务绑定，核对生命、模式、许可版本、插件能力和运行代次。
2. 绑定有效且宿主历史可恢复时，M14 在作用域配置完成后恢复；没有有效执行载体时创建新的载体，仍绑定同一生命/场景/任务。
3. 能力、提示词及来源范围在首次输入前配置；不能先触发模型，再补权限。宿主的全局 session 创建事件也要核对，不能假定 setup 覆盖所有早期钩子。
4. 缺失宿主日志时，依据权威事件和工作段恢复到新载体；不能悄悄用空白会话继续，也不保证恢复不存在的原历史。
5. 需要轮换时先暂停新输入分派、等待或取消在途执行、保存覆盖与未处理尾部，再原子切换应用层有效绑定。旧载体结果不再能提交新动作，但其真实晚到回执仍应记账。
6. 宿主会话变更和 LifeCore 库不是一个天然原子事务。绑定的准备/启用/退休及崩溃核对规则由 M02/M13/M14 定义；未取得有效绑定的 Agent 不获得正式外发执行资格。

本文不规定每条消息都轮换，不锁定“一个工作段必须对应一个物理 session”。先复用连续执行和明确交接；P3 决定 DSH 压缩与工作段如何协调。

## 6 数据归属：逻辑权威与物理保存分开

“逻辑权威”决定数据含义、有效版本与谁有权修改；“物理保管者”负责具体文件、数据库或日志。两者可以不同，但每类正式状态只能有一个明确当前版本。

| 数据 | 逻辑权威 | 物理保管候选 | 同步与限制 |
| --- | --- | --- | --- |
| 生命 ID、出生原稿、确认版本 | M01 | LifeCore 持久存储 | DSH/插件获得带版本的只读投影，不反向修改出生档案 |
| 当前人格与修订历史 | M07 | LifeCore 持久存储或满足契约的领域组件 | 各场景读同一正式版本的获准投影，插件 persona 文件不能独立成为另一权威 |
| 人物绑定、关系与情绪状态 | M06/M05 各管自己的状态 | LifeCore 或受控组件 | 对象与来源明确；记忆中的关系描述不直接更新关系权限 |
| 授权、撤销与可信管理身份 | M12 | LifeCore 授权存储；宿主认证由 DSH 管 | 不能从聊天、记忆抽取或插件建议推导新授权 |
| 规范经历与允许留存的来源 | M03 | LifeCore 事件存储；符合保存/删除契约的外部来源库可作为载体 | 来源指针必须可恢复且有版本；仅临时路径或可随意清理的 session ID 不够 |
| 工作段、交接、活动/任务与检查点 | M09/M08 | LifeCore 持久存储，允许受管后端 | DSH inbox 是执行队列，不替代承诺和长期任务状态 |
| 记忆事实、经历表达、图与索引 | M04 | 待选记忆后端；具体采用“派生服务”还是“某类记忆唯一权威”待 R03 | M04 负责语义和访问规则；不得同时保留两套可独立改写的当前事实 |
| DSH session、模型/工具执行记录 | DSH | 已挂载的 DSH 持久会话后端 | 保留宿主记录职责；不复制完整技术日志作为第二份人生，也不把渲染记录当唯一外部回执 |
| 出站动作、执行许可、实际回执 | M11 | LifeCore 动作账本；插件返回外部结果 | 宿主 tool/result 与平台成功分开；流式文本或模型完成不等于 QQ 已发送 |
| 平台登录态、凭据、媒体缓存 | 对应宿主或能力插件 | 原组件凭据管理/数据目录 | LifeCore 保存关联与状态，不再复制明文登录态；删除/卸载需要清单化处理 |
| 用量与费用 | 原执行方提供实际记录；M02 负责预留，M15 汇总 | DSH、插件账单及 LifeCore 关联账本 | 同一调用不重复计费；未知费用单列，不填成零 |

统一生命记录不意味着所有原始工具输出都永久保存。M03 按留存规则选取必要证据、来源标识和结果，DSH 原日志按其用途保留；确需证据副本时明确出处与删除关系。最终保留期限和备份规则在 R06/P2–P3 决定。

### 6.1 跨存储写入的边界

若记忆库承担派生物：来源与待整理工作先持久接收；按来源 ID/版本形成幂等整理任务；插件返回或写入派生结果后登记覆盖。崩溃重试不能生成重复成长证据，失败不能把 pending 标成已整理。

若记忆插件承担某类记忆的唯一权威：LifeCore 通过稳定接口更新，保存后端引用和版本，不再同步维护另一份可直接编辑的当前事实。它必须支持纠正/删除、访问限制、版本回查与恢复；否则该权威方案不成立。

上述两种方案都需要明确“更新中/已确认/失败/需核对”的状态。新纠正或删除在后端同步完成前，要阻止旧内容继续进入模型；不能以两个库最终会一致为由继续使用已失效材料。具体协议留给公共契约设计，不声称跨插件分布式原子提交已经存在。

## 7 能力如何进入大肥鱼的执行范围

把安装与启用分开：管理员安装插件后，M14 核查能力和版本，配置账号/数据位置，登记需要的权限和费用，满足契约的能力才进入指定场景。模型提出想获得某能力，只形成可审阅建议，不自行安装、登录或扩大权限。

| 能力类型 | 默认接入方式 | 需要补的生命规则 |
| --- | --- | --- |
| 搜索、字幕/评论等只读工具 | 尽量直接复用 DSH 工具注册与执行 | 输入来源、可读账号范围、网络出站、用量和结果证据 |
| 播放/暂停/定位等资源操作 | 通过带活动归属的适配调用现有能力 | 播放器唯一使用者、检查点、实际读回，不能恢复已经换掉的视频 |
| 社交发送、发说说、头像等外部写入 | 经 M11 形成明确动作后调用执行能力 | 当前许可、目的地、内容版本、尝试 ID、外部回执和未知状态 |
| 记忆工具及自动钩子 | 选定正式空间、范围和后台角色后接入 | 原始证据、提炼覆盖、隔离、纠正/删除、预算及自动注入归属 |
| 完整自主生活插件 | 配置关闭独立决策，或适配为受管活动执行器 | 统一身份、作息、暂停、取消、费用和记录；做不到则不直接并用 |
| 工作工具 | 仅任务作用域授予所需能力 | 文件/网络/接收方范围、子任务约束、产物核验和取消 |

### 7.1 工具调用与动作账本如何衔接

对于可直接复用的读工具，在指定 DSH 执行管道完成范围和预算检查，记录最小必要观察；不要为每次读操作另建一套模型循环。

对于写工具，选择一个经过验证的受控入口：可以在原工具执行之前持久准备动作并核对许可，也可以用薄适配工具把执行交给 M11。两种方式择一；模型看到原始写工具和适配写工具同时可绕行的组合不允许启用。

动作与尝试标识由可信执行上下文生成并关联，不能仅相信模型传入的 action_id。外部调用前须有可恢复记录；回执进入 M11 后再成为正式经历。若插件绕开工具管道直接后台外发，必须控制该入口，工具名称白名单本身无效。

某些工具在宿主取消后只返回 ABORTED，外部却可能已经完成。没有可靠外部回执时登记 unknown；有可靠晚到回执则更新实际结果，但不允许旧执行继续后续动作。新的授权不会自动触发旧 unknown 动作重试。

### 7.2 作用域不是完整安全边界

DSH 的注册作用域和工具限制适合控制模型获得的能力，不自动隔离同进程插件的文件、网络、数据库访问。global hooks、自动提炼、独立 HTTP API、子进程和已有凭据都需要纳入接入审查。

当前官方工具文档说明：restrict 约束继承的全局工具，作用域内新注册工具仍可见；只改工具的显示文本也不会移除程序调用者取得的原始返回值。因此须核对最终可执行集合、注册来源、执行策略和原始结果访问，不能仅查看聊天里出现哪些工具名。

无法控制的插件不能靠一段“不要越权”的提示词获得正式授权。先配置关闭或限制功能，再考虑受控补丁/进程隔离；如果仍无法满足要求，记录为不兼容，而非静默放宽生命规则。

## 8 同一人格怎样在多个上下文中保持一致

各执行上下文在每个安全步骤边界读取当前正式身份/人格版本与必要状态投影。私聊、群聊、工作使用不同材料和表达约束，但不维护互相竞争的“大肥鱼是谁”。

关系和状态变化通过 M02 提交后供其他场景读取；不要把 A 场景的整个私聊记录广播到 B 场景。允许分享的是获准事实或活动投影，不是所有来源。工作任务运行时只取得必要任务资料，不默认载入主人全部隐私与共同经历。

版本检查按依赖区分：授权撤销、删除和正式身份修订需要阻断受影响旧结果；与当前答案无关的其他场景事件不应取消所有执行。具体冲突合并规则在 M02 设计，不能用一个全局变化计数使并行生活永远失效。

长时间工作任务会从安全边界更新身份与许可；不为了更新人格重复执行已完成步骤。插件自带系统提示仅贡献能力用法，不另加与正式人格冲突的人设；发生冲突要在作用域装配阶段解决。

## 9 上下文、记忆与压缩的责任

M09 决定本轮需要且有权使用的材料；DSH systemPrompt 与执行循环负责把允许的贡献和工具形成实际请求；记忆插件提供候选或受控注入。M14 必须能核对最终请求，不只核对 LifeCore 最初准备的内容。

原方案中的“每轮独立 ModelTask 自行组装全部上下文”不再作为默认推荐。本稿建议先复用场景连续执行；是否保留物理 session、何时压缩或轮换在 P3 比较后确认，明确改变旧稿推荐的部分必须记入决策记录。

一个工作段只指定一个负责压缩的流程。若使用 DSH 压缩，LifeCore 记录其覆盖和交接状态，不对同一范围再运行竞争性摘要；长期记忆提炼有独立目的和覆盖记录，不能把压缩摘要冒充唯一原始证据。

记忆插件可能有工具检索、固定 context、自动召回、夜巡等多个入口。选择“插件受控注入”或“LifeCore 取候选后注入”作为具体路径，不能既全部自动注入又重复手工加入相同材料。开关覆盖范围和最终请求必须验证；关闭主动联想不等于关闭身份连续性或明确回忆。

## 10 一条完整消息如何经过这套分工

以“大肥鱼看视频时，你在 QQ 问她在做什么”为例：

1. SnowLuma 接收消息；M10 核验账号、发送者、场景与平台事件标识。
2. M03/M02 持久接收获准原始材料及待处理工作；相同事件不会提交给两个回复者。
3. M08 提供当前活动状态并判断是否需要暂停。要暂停时由 M11/M10 调插件执行，并读取实际状态；不能先假设暂停成功。
4. M09 取得当前人格、此人的获准关系/回忆和可分享的活动快照。活动涉及其他人的私密内容时投影不得暴露标题、链接或存在细节。
5. M14 查找/恢复此 QQ 场景的 DSH 执行绑定，附上本轮许可和材料；DSH 驱动模型及必要的只读工具调用。
6. 模型返回回答候选。DSH 流式输出可以作为本机管理预览，但不能被另一个平台插件自动转发到 QQ。
7. M02/M11 再核对候选依赖、当前授权和发送目标，保存动作后调用发送能力。生成成功和发送成功分别记录；超时为未知，不自动重发。
8. M03 保存实际结果，M04 按既定整理策略处理新增经历；不是每轮都强制调用全部情绪、人格和记忆模型。
9. M08 根据最新消息、任务、权限与资源重新决定继续看视频还是做别的事；恢复前核对视频标识和检查点，不自动执行过期续播回调。

其他场景共同遵守同样的身份、授权、结果约束，但不要求所有读取都走写事务，也不要求等待模型/浏览器时占住全局提交队列。

## 11 生命周期与故障边界

| 情况 | LifeCore 的责任 | DSH/插件的责任与待核实事项 |
| --- | --- | --- |
| 插件缺失/卸载 | 撤销能力准入、标记相关活动受阻，身份与已有经历不变 | DSH 清理注册/依赖；插件释放资源，是否有残留后台任务需验证 |
| 全局暂停 | 持久阻止新动作与新活动，冻结未执行工作，记账晚到结果 | 停止 Agent 的新步骤和受管定时器；已开始操作为协作取消，不能保证远端撤回 |
| 活动暂停 | 仅暂停目标活动，保留其他获准聊天与任务 | 播放器/工具须给出真实检查点；不把全局停止当局部暂停 |
| 权限撤销或来源删除 | 使受影响绑定/步骤失效，阻止旧材料进入后续请求和外发 | 更新工具与注入范围、处理已有上下文；已发给模型的内容无法假装从未出站 |
| 宿主关闭/崩溃 | 持久绑定、活动、待处理事件、动作和待核对状态 | 正常关闭排空日志和释放句柄；崩溃后不能假定所有 pending 均未执行 |
| 重启恢复 | 先载入身份与撤销/删除状态，再核对能力和动作，再开放执行 | 配置受控 Agent 不能在核对前自动处理旧 inbox；保留/丢弃/重派待处理输入由恢复协议决定 |
| 记忆后端不可用 | 保留可安全保存的新事件、显示受阻；不换空库或伪称长期记忆正常 | 停止依赖该后端的正式回复准入；管理诊断仍可用。后续若要限功能聊天须单独明确模式 |
| 插件升级 | 暂停相关能力，核对版本/数据格式/接口，必要时准备迁移 | 不能恢复旧版本无法解释的数据；检查成功后才重开能力 |

硬预算不是一个 UI 总计。插件独立模型调用若不能预留、限制或可靠停止，就不能承诺统一硬上限；应先限制该路径或明确不接入。取消后仍可能产生在途费用，要记录实际用量和无法核实部分。

## 15 本轮形成的建议与后续顺序

本轮形成六项供核对的设计建议：

1. 采用“生命规则＋DSH 执行＋插件能力”，保留单一身份和可替换实现。
2. 按场景/任务隔离执行上下文，优先复用连续会话；生命、活动和原始经历不依赖某个 Agent 常驻。
3. 数据按类别明确逻辑权威与物理保管者；记忆后端选择与是否保留 Python 分开决定。
4. 内容读取优先直接复用工具，外部写入经可恢复的统一动作入口；原始工具、后台入口不能绕行。
5. 上下文只有一个协调者，插件自动注入和后台整理必须可控；具体压缩路线留到 P3。
6. 插件加载不自动获得大肥鱼的身份、数据和外发资格；生命周期与跨场景准入是集成的一部分。

R01/R02 状态更新为“已形成建议稿，待确认”，不是“已决定”。本稿可据反馈修订，不据此开始开发。

共同契约已在[03 建议稿](2026-11-02-common-contracts.md)细化 M01/M02/M03/M12/M13/M14 的出生与事件接收、执行绑定、许可、动作和恢复状态，并带入 A01–A12。依赖本稿建议的内容继续标注前提；前提尚未确认时不冻结接口。后续用同一套契约比较 LivingMemory/SeekMemory，核对职责兼容性后再安排实施。
