# LifeCore 设计梳理 06：SeekMemory 服务与 PLUR 检索的选型建议

日期：2026-11-02（Asia/Shanghai）。状态：R03 选型建议，待确认；仅静态研究和文档整理，未开发、安装或运行候选。

承接：[04 复用评估](2026-11-02-memory-context-reuse-design.md)、[05 适配契约](2026-11-02-memory-adapter-contracts.md)、[各候选改动地图](2026-11-02-memory-adapter-change-map.md)。本稿收敛接入范围，不重定义来源、权限、幂等、删除或恢复协议。用户要求给建议，不等于已选定供应方或批准实施。

后续收敛：[07 组件、提交边界与准入标准](2026-11-02-memory-integration-boundaries-design.md)补充窄依赖替换、T1–T5 提交边界及验证顺序；其中 app.ports 的传递导入需要裁剪，不能只凭无写入函数判断可独立加载。

## 1 建议及成立条件

**建议首选 SeekMemory 的受控记忆服务路线，PLUR 检索组件保留为备选；首期不同时集成两套。** 这里的服务是 LifeCore 管理的库级门面，不是安装完整 SeekMemory DSH 插件，也不是新增一个需要用户管理的服务器。

理由是当前目标同时包含“自主记住重要事情”和“找回记忆”。SeekMemory 已有不落库的候选构造入口，可复用结构化抽取、证据来源检查及时间筛选等机制。PLUR 的这条候选路线只复用检索，仍需我们建立候选抽取、纠正协调与记忆整理流程。对“少开发重复功能”的目标，前者更值得优先采用。

这个推荐不是性能排名。SeekMemory 已读检索器是图关联＋BM25，尚不能证明满足中文语义召回；必须补入受控语义检索并完成质量验证。PLUR 已有词法＋向量融合，但独立混合检索未作为公共入口导出，不能按一个现成的轻量包计价。两者都没有通过本项目运行验收。[证据 S1–S4、P1–P4](#8-固定源码证据)

**决定能否落地的两条红线：** SeekMemory 的候选处理必须能保持无自主写入、无独立人格/后台运行；中文语义检索必须在相同数据与预算下达到项目要求。如果最终需要重写候选构造、时间检索和大部分依赖，其复用收益就消失，应改用 PLUR 检索＋LifeCore 自建整理。不能为了保留推荐而放宽共同契约。

## 2 用相同产品范围比较

两条路线均须交付：共同经历与重要信息自动保留；可查看、纠正和删除；中文语义回忆；正式/试聊和不同私聊隔离；来源可追溯；主动联想开关；暂停、恢复和可移植导出。关闭主动联想不关闭显式回忆与记忆保存。仅能搜关键词的阶段属于未完成功能，不能称最小合格版本。

| 比较项 | S：SeekMemory 受控记忆服务 | P：PLUR 检索组件 |
| --- | --- | --- |
| 复用中心 | 抽取提示、解析/候选构造、时间/重要性相关规则、部分召回算法 | 词法检索、向量检索及缓存、融合排序、降级状态 |
| 最小外部入口 | 自建薄门面调用候选构造与受控检索模块 | 自建薄门面调用从固定源码拆出的检索入口 |
| 领域记忆权威 | LifeCore M04/M13 | LifeCore M04/M13 |
| 首期独立后端主库 | 不引入 SeekMemory 主库；规范记录生成受限 Artifact 视图 | 不引入 PLUR YAML/PG 主库；规范记录生成受限 Engram 视图 |
| 最大新增能力 | 受控中文语义检索；把上游推断变成可校验候选 | 自动抽取、重要性判断、版本纠正及整理算法；适配检索包 |
| 主要长期负担 | 跟踪抽取/候选规则与字段变化，维护语义检索接线 | 维护自研记忆算法，跟踪内部检索依赖和模型缓存 |

“LifeCore 权威”不要求永远使用自写存储引擎。但本次最小方案选择已有 Python 内核中新增规范记忆存储，避免再引入一个权威相近的插件库。两条路线采用同一选择，便于公平比较。现有内核只是底座，不等于 05 的记忆协议已完成。今后若委托 SeekMemory 仓储承载规范权威，须单独设计事务所有权与迁移，不能偷偷把两个 commit 合成一个成功。

## 3 S 路线的最小接入范围

### 3.1 保留、适配与排除

| 模块边界 | 最小用法 | 所需工作 |
| --- | --- | --- |
| `perceive/extract.py` → `build_prompt` | 保留结构化抽取提示的基础，模型调用由 LifeCore 网关发起 | 加入固定 source_revision/representation 与精确证据约束；启用证据要求，未通过校验的结果不提交 |
| `perceive/absorb.py` → `build_plan` | 保留解析和候选构造；输入仅是获准的消息与记忆视图 | 把返回 Artifact 转成 Candidate；重新确定可信 realm/subject/policy。上游按会话字符串推断的 shared/private 不能生效；上游随机 ID 不能承担业务幂等 |
| `core/artifact.py` 等值对象 | 只作为处理器内部表示 | 与规范 MemoryVersion/EvidenceRef 做显式映射，禁止模型提供字段升级授权 |
| `recall` 的时间、词法和排序逻辑 | 作为受控 Recall 门面的算法组件 | 索引构建前已授权；返回结构化 ID/版本/依据。完整 `query_block` 的字符串装配不作为 M09 最终上下文 |
| 图关联 | 首期可关闭；需要时只给授权诱导子图和同范围缓存 | 原 `activate` 会走图邻居，不能只过滤最终 pool；缺数据或权限未知时不采用其宽松存活回退 |
| 语义检索 | 在同一个 Recall 门面内补充受管 embedding 与向量检索 | 复用模型/向量基础设施，自己接版本化投影、权限、融合和降级；不自研训练 embedding 模型。具体模型待相同中文样本验证 |

不实例化 `IngestService` 的整套写流程、`ServiceCollection`、AgentRuntime/worker、DSH host、persona 刷新、dream/maintenance 后台、指定记忆自动写回或独立消息注入。候选由 LifeCore 持久任务驱动，实际提交只经过 M04。已经存在的 `build_plan` 使这个分离有源码依据，但递归导入的无副作用性仍需后续验证。

不把 `store/artifacts.py` 的 CAS/版本表算作本最小方案已节省的开发量：它们确实可复用，但本方案没有接它的数据库。直接使用 `Store` 会创建来源、提炼、runtime、dream 等仓储并由各仓储管理事务。为省几张表而增加第二套写入与迁移责任，当前不划算。[S5–S6](#8-固定源码证据)

### 3.2 完整调用流

1. M03 原子保存来源修订与持久整理任务；新纠正立即建立“当前事实待协调”屏障。
2. M12 为任务签发可信输入范围及模型出站许可。调度器按任务预算取已授权正文、固定表示和可见旧记忆；不得把整个缓存交给抽取器。
3. 网关调用模型；SeekMemory 解析和 `build_plan` 产生候选。候选经确定性身份映射、逐断言证据校验、策略约束、纠正冲突检测后，交给 M04。
4. M04 原子提交规范版本、operation result、依赖及 outbox。**候选没有通过不等于来源未保存；模型调用成功不等于记忆提交成功。**
5. 投影器生成受限 Artifact/词法/向量表示；以 05 的完整性、代次和连续水位协议发布。首期不持久化另一份 SeekMemory 权威 Artifact 库。
6. 回忆时，M12 先裁定允许候选；受控召回返回 ID/版本与匹配依据；M04 复核当前状态并回填规范内容，M09 统一装配，模型出站前再查授权。
7. 删除/纠正先阻断可见性，随后清理规范派生闭包与缓存；导出从规范数据生成。恢复后重建派生层，不执行历史整理的自主副作用。

部署上优先复用现有 Node 宿主＋Python 内核，不另设常驻公开服务。受管任务在内核中调度，模型等待和耗时计算不得占住领域写事务；CPU 密集检索若需要 worker，也由插件托管并遵守暂停/取消。是否需要额外 worker 是性能测量后的实现选择，不增加用户运维步骤。[本地 kernel-client](../../../src/kernel-client.js)

## 4 P 路线的最小接入范围

### 4.1 真正的组件边界

候选集合输入 `hybridSearchWithMeta`，经 BM25、向量相似度和融合产生结果；reranker 首期关闭。可以保留 FTS 的汉字相邻双字切分，但它不证明中文语义质量；单字检索、长中文段落和改写问法都必须纳入样本。

已读 `@plur-ai/core` 的 exports 只有包根，构建入口也只有 `src/index.ts`。根导出部分 embedding/RRF 原语，**没有导出完整 `hybridSearchWithMeta`**。因此有两个实际办法：

- 本路线默认：从固定提交维护一个有来源清单的检索子包，显式导出所需函数并裁剪依赖。闭包至少涉及 hybrid-search、fts、embeddings、embedders、query rewrite、sync/cache、logger，以及有关状态/类型；须补查递归 import，不能宣称复制两三个文件即完成。
- 如果上游以后提供稳定独立入口，可替换子包。只用当前公共 `embed` 和 RRF 再自建词法/融合管道也是可行方案，但那是另一种更小的算法复用，不能冒充现成混合检索接入。

不以安装完整 core 后深路径 import 作为稳定方案；不实例化完整 `Plur`、DSH plugin、autoLearn/autoCapture、人格指令注入、远端同步或主存储。主包声明的 PGlite、YAML 等依赖不会因为我们只调用一个函数自动消失；能否从独立构建中裁掉要验证，不把“未启用数据库”写成“包没有数据库依赖”。[P1–P2](#8-固定源码证据)

### 4.2 缓存和模型也是适配范围

`embeddingSearch` 会读写 `.embeddings-cache.json` 及增量文件；未传 storagePath 会落到默认相对路径。因此最小接入也必须提供受管路径、命名空间、删除登记和旧写隔离，不能把它当纯内存函数。

首期建议以 realm＋backend_generation＋授权分区划分持久缓存；向量键绑定规范记忆版本与 embedding 身份。允许集合变化导致的残留向量要纳入删除闭包；任务只能读取属于其许可范围的缓存视图，不能先装入混合私聊缓存再按候选过滤。不支持安全细粒度清理时，先废弃受影响代次并重建，旧代次等待尾部写终止后再清除。

当前 embedding 选择与状态有进程级缓存/配置；若多个生命域需要不同模型或出站许可，需改成实例级依赖注入或分 worker 隔离，不能临时切换全局环境变量。默认模型为 `bge-small`（源码指向英文模型）；不能以默认配置承诺中文效果。选择本地多语模型或获准远端模型须同时比较质量、下载/内存与调用费用。[P3–P4](#8-固定源码证据)

取消查询不证明所有缓存副作用已停止：实现有分段保存和延迟合并路径，真正的暂停/删除须等待受管任务核对，或隔离旧代次。查询降级要向 M09 返回 `hybrid-degraded`/不完整原因；不能把无语义结果伪装为完整召回。[P3](#8-固定源码证据)

### 4.3 完整调用流及新增工作

来源接收→**LifeCore 自建抽取/重要性筛选/候选构造**→共同 M04 提交→受控 Engram 投影→授权候选输入 PLUR 检索→ID/版本映射→M04 当前状态复核→M09 装配。不要用 `Plur.learn` 创建投影，也不把 `forget` 当规范删除。

Engram 的 id 使用规范版本/块的稳定投影 ID。上游检索返回的是 Engram 对象，门面只返回受控 ID、版本、匹配诊断，不让其中旧正文或 scope 成为事实/许可权威。缓存、完整块 manifest、索引代次与失效采用同一 05 契约。

本路线复用的是检索组件，自动记忆处理器需自己设计提示、解析、证据约束、重要性/时间提取和冲突协调。PLUR 根导出的 `extractLearnings` 可作为另一个候选算法评估，但本轮未验证它适合共同经历与中文自动保留，不能把整套学习能力记为该最小路线已包含。

## 5 自研工作：共同底座与路线差额

| 工作包 | 两者共同且不能省略 | S 的额外工作 | P 的额外工作 |
| --- | --- | --- | --- |
| 来源与证据 | 稳定身份、修订/表示、精确片段、任务接收事务 | 上游来源 ID、推断 scope、缺证据兼容路径转换 | 规范记录到 Engram 字段/块映射 |
| 自动整理 | 持久调度、预算、模型网关、证据真实性与纠正裁决 | 适配现有提示/候选规则；重要性策略需按产品校准 | 自建抽取、解析、重要性/时间候选逻辑与质量集 |
| 领域写入 | CAS、幂等结果、冲突、依赖图、outbox、删除抑制 | 不采用内部自主写和关系/人格修订 | 不采用重复 learn/强化写入 |
| 回忆 | 先授权、后检索、末次复核，M09 唯一装配 | 受限缓存/图、结构化返回；补语义投影与融合 | 拆检索子包；实例化模型/缓存；中文模型验证 |
| 删除/恢复/导出 | 独立控制账本、闭包、尾部隔离、一致快照、导入代次 | 覆盖受控派生视图/索引；不用上游全库恢复 | 覆盖向量主/增量缓存和延迟写；不用 PLUR YAML 作为完整备份 |
| DSH 上下文 | 受控压缩、引用/日志清理、实际注入记录 | 与 P 相同 | 与 S 相同 |

两条路线都不能省下生命的身份、人格演化、关系规则、授权、行动回执。这些是大肥鱼核心语义。可省的是已有记忆处理算法和基础设施的重复开发，不是把完整生命交给记忆插件。

## 6 后续维护成本

下表是依据改动面作出的相对判断，不是人日估算；尚无同条件运行数据。总成本应把共同底座、路线适配、算法质量、运行费用、升级及迁移分别记账。

| 成本类型 | S：SeekMemory 服务 | P：PLUR 检索 |
| --- | --- | --- |
| 初次接入 | 中高：已有候选入口，但要固定依赖、适配证据/权限并补语义链 | 检索接入中等；达成完整自动记忆目标为高，新增整理逻辑较多 |
| 自研行为维护 | 中高：继承候选规则，仍需纠正误记、证据和产品策略 | 高：抽取、记忆筛选、时间和矛盾处理的质量主要自己负责 |
| 上游升级 | 候选字段/解析/内部导入变化会影响门面；固定提交，按需吸收 | 内部检索没有独立公共契约；每次升级核对 tokenizer、cache、embedder 和依赖闭包 |
| 日常运行 | 抽取模型费用＋自选语义模型费用/资源 | 自建抽取同样有模型费用；检索还涉及模型加载、缓存与可选远端 embedding |
| 数据维护 | 规范主库和派生层；本最小方案不再维护 SeekMemory 主库迁移 | 规范主库和派生层；缓存主/增量合并与旧写清理需额外关注 |
| 版本迁移 | 规范数据不随候选升级强制改格式；规则/表示变化新建 processor/projection 版本 | tokenizer/模型身份变化需新代次重建，不把换维度当普通覆盖 |
| 质量回归 | 重点是抽取证据、纠正与中文回忆 | 同样需要抽取回归，另检查词法/向量融合和降级行为 |
| 替换退出 | 停处理器，规范数据保留，替换算法/索引；抽取规则仍有行为依赖 | 停检索器，保留规范数据并重建投影；组件退出较容易 |

维护方式建议固定为：保存上游 SHA、许可/NOTICE 与修改清单；固定依赖；统一从门面调用；升级只接纳具体收益或修复；先进行契约与质量回归，再切换代次；不自动追主分支。依赖清单、安全修复和本地模型制品都属于维护成本。本轮不做许可证法律结论或供应链准入认证。

**不建议现在追求“零 fork”。** 使用未公开内部接口本身也形成隐性维护分支。要么维护小而明确的受控源码包，要么推动上游稳定接口；不要把隐性成本记为零。SeekMemory 也按固定源码组件管理，不预设已有稳定独立 SDK。

## 7 选择依据与后续顺序

| 条件 | 选择建议 |
| --- | --- |
| 当前目标保持：自动记重要经历，减少完整记忆算法自研 | 选 S，先复用候选与检索机制，补齐受控中文语义链 |
| 团队已有成熟自动整理管道，主要缺检索 | 选 P，SeekMemory 的额外规则价值变小 |
| S 无法在候选层隔离自主写入/权限，或需要大面积重写核心算法 | 放弃 S，转 P；保留规范权威与共同契约 |
| P 的独立打包仍需引入大部分运行时，或全局模型/缓存无法受控 | P 也不能准入；先缩减组件方案，不退回完整插件绕过要求 |
| 两者检索质量不达标 | 调整模型/分块/检索候选，不用关键词回退宣布语义目标完成 |

接下来仍可先完成以下设计交付，不直接进入编码任务：

1. 固定 S 门面与依赖清单：明确保留的候选/检索模块及不可进入的宿主、写入、后台路径；同时记录 P 的替换接口。
2. 画定唯一写入事务与持久任务边界，确认规范数据、缓存、独立控制账本分别在哪里，以及每一处删除责任。
3. 固定中文质量样本与成本预算：同义改写、否定/纠正、时间变化、同名人物、私聊隔离、单字与长文本；同样本比较完整管道，不能只比检索函数。
